# 프로젝트 1 비교분석보고서
## 퀴즈 채점 자동 알림 시스템 (Make vs Zapier)

---

## 1. 프로젝트 개요

| 항목 | 내용 |
|------|------|
| **주제** | 구글 폼 퀴즈 응답을 자동 채점하여 합격/불합격을 디스코드로 알림 |
| **데이터 흐름** | Google Forms(응답) → 조건 분기(점수 판별) → Google Sheets(기록) → Discord(알림) |
| **합격 기준** | 점수 **8개 이상** → 합격 / **8개 미만** → 불합격 |
| **사용 도구** | Make(구 Integromat), Zapier |
| **목적** | 동일 시나리오를 두 노코드 툴로 구현하여 UI/UX·과금·연동 방식 등을 비교 |

## 2. Make 구현

### 2-1. 워크플로우 구조
```
Google Forms (Watch Responses)
        │
        ▼
     Router  ──1st──▶ Google Sheets (Add a Row) ──▶ Discord (Send a Message)   [불합격 경로]
        │
        └────2nd──▶ Google Sheets (Add a Row) ──▶ Discord (Send a Message)   [합격 경로]
```
- **핵심 특징:** Make는 **Router 모듈 하나**로 여러 갈래의 조건 분기를 만들 수 있음.
- 각 경로에 필터(점수 조건)를 걸어 합격/불합격을 나누고, 경로별로 시트 기록과 디스코드 알림을 각각 실행함.

![Make 구성 화면](images/make_config.png)

*설명: Google Forms → Router → (합격/불합격 2경로) Google Sheets → Discord 전체 흐름. 하나의 Router로 두 조건 경로를 한 시나리오 안에서 처리.*

## 3. Zapier 구현

### 3-1. 워크플로우 구조
```
Google Forms (New Form Response)
        │
        ▼
Filter by Zapier (Total Score 조건)
        │
        ▼
Google Sheets (Create Spreadsheet Row)
        │
        ▼
Discord (Send Channel Message)
```
- **핵심 특징:** Zapier의 Zap 하나는 **단일 경로(선형)** 구조.
- Filter 모듈에서 **하나의 조건 흐름만** 처리하므로, 합격/불합격 **두 조건을 하나의 Zap에서 자동 분기할 수 없음.**

### 3-2. 구성 화면 (조건 2개 분리)
> 📷 **[이미지 3] Zapier 구성 화면 ① - 불합격 조건 (Total Score is less than 8)**

![Zapier 구성 - 불합격](images/zapier_config_fail.png)

*설명: Filter conditions에서 `Total Score is less than 8` 로 설정 → 8 미만이면 계속 진행하여 "불합격" 알림.*

> 📷 **[이미지 4] Zapier 구성 화면 ② - 합격 조건 (Total Score Greater than 7)**

![Zapier 구성 - 합격](images/zapier_config_pass.png)

*설명: Filter conditions에서 `Total Score (Number) Greater than 7` 로 설정 → 8 이상이면 계속 진행하여 "합격" 알림.*

> ⚠️ **Zapier의 한계 (직접 확인한 단점):**
> Zapier의 Filter는 **하나의 Zap 안에서 조건에 따라 경로를 나눌 수 없음.**
> 따라서 **합격용 Zap 1개, 불합격용 Zap 1개를 각각 따로 만들어야** 했음.
> → 같은 워크플로우가 **2벌로 중복 제작**되어 관리 포인트가 늘어나는 단점.
> *(참고: Zapier의 Paths 기능으로 분기가 가능하나, 이는 상위 유료 플랜에서 제공됨 — 무료/스타터 플랜에서는 Filter로 Zap을 나눠야 함.)*

## 4. Make vs Zapier 비교 분석

### 4-1. 종합 비교표

| 비교 항목 | Make (Integromat) | Zapier |
|-----------|-------------------|--------|
| **UI/UX** | 노드(모듈)를 캔버스에 자유 배치, 흐름을 시각적으로 파악하기 쉬움 | 위→아래 선형 리스트 구조, 직관적이고 단순함 |
| **조건 분기** | **Router 모듈**로 한 시나리오에서 다중 경로 분기 가능 ✅ | Filter는 단일 흐름만 처리, **분기하려면 Zap을 분리**해야 함 ⚠️ (Paths는 상위 유료) |
| **설정 난이도** | 자유도가 높은 대신 처음엔 다소 복잡 | 단계별 설정이 쉬워 입문자에게 친숙 |
| **연동 범위** | 다양한 앱 + 강력한 데이터 가공(함수, 이터레이터 등) | 앱 연동 수가 매우 많음(생태계 큼), 가공은 상대적으로 단순 |
| **실행/로그** | 각 모듈별 입출력 데이터(번들)를 상세히 확인 가능 | 단계별 실행 히스토리와 오류 로그 제공 |
| **과금 방식** | **Operations(작업 수)** 기반 — 실행된 **모듈 하나당 1 operation 차감** | **Tasks(작업 수)** 기반 — 성공한 **액션 하나당 1 task 차감** (트리거는 무료) |

### 4-2. 과금 방식 상세 (중요)

두 도구 모두 **"실행 횟수 기반"** 과금이며, "상시 켜져 있으면 계속 차감"되는 방식이 **아님.**
트리거가 감지되어 워크플로우가 **실행될 때마다** 그만큼 차감됨.

| 도구 | 과금 단위 | 차감 기준 | 예시 |
|------|-----------|-----------|------|
| **Make** | Operations | **모듈(단계) 하나 실행 = 1** | Forms→Router→Sheets→Discord 경로 실행 시, 실행된 모듈 수만큼 차감 |
| **Zapier** | Tasks | **액션 하나 성공 = 1** (트리거·필터 통과는 task 미차감) | Sheets 기록 + Discord 발송 = 2 tasks |

> 🔴 **제출 전 필수 확인:** 요금 정책과 무료 플랜 제공량(Make operations / Zapier tasks 개수)은 **자주 변경**됩니다.
> **Make 공식 요금 페이지**와 **Zapier 공식 요금 페이지**에서 최신 수치를 반드시 직접 확인 후 기재하세요.

## 5. 결론

| 구분 | 요약 |
|------|------|
| **Make가 유리한 점** | 하나의 시나리오에서 **Router로 다중 조건 분기**가 가능해, 합격/불합격을 한 번에 구성할 수 있어 관리가 효율적 |
| **Zapier가 유리한 점** | 선형 구조로 **입문자가 배우기 쉽고**, 앱 연동 생태계가 매우 넓음 |
| **이번 과제 체감 차이** | 같은 시나리오에서 Make는 **1개 시나리오**로 끝났지만, Zapier는 **합격/불합격 Zap 2개**를 따로 만들어야 했음 → **분기 로직이 필요한 프로젝트에서는 Make가 더 편리** |

**한 줄 요약:** 단순 선형 자동화는 **Zapier**, 조건 분기가 많은 복잡한 자동화는 **Make**가 적합하다.

>

### 2-3. Make 특징

## 3. Zapier 구현

> ⚠️ **Zapier의 구조적 특징**: 하나의 Zap(Path/조건 분기)에서 **여러 조건을 동시에 한 번에 넣기 어려움**.
> 따라서 **PASS 조건**과 **FAIL 조건**을 각각 별도의 경로(Path)로 나누어 구성해야 하므로 화면이 2개로 분리됨.

## 4. 핵심 비교 분석

| 비교 항목 | Make | Zapier |
|-----------|------|--------|
| **UI/UX** | 노드(선) 기반 시각적 구성, 흐름 파악 쉬움 | 단계별(Step) 리스트 방식, 초보자 친화적 |
| **설정 난이도** | 다중 조건 분기가 한 화면에서 가능 (상대적 편리) | 조건마다 경로 분리 필요 (다소 번거로움) |
| **조건 분기** | Router 1개로 여러 갈래 분기 가능 | 한 Zap에 여러 조건 동시 처리 어려움 → **경로 분리 필요** |
| **연동 범위** | 1,000+ 앱 연동 | 6,000+ 앱 연동 (연동 앱 수는 더 많음) |
| **무료 플랜** | 월 1,000 operations | 월 100 tasks (상대적으로 적음) |
| **실행 로그** | 상세한 실행 히스토리 + 각 모듈별 데이터 확인 | Task History로 성공/실패 확인 |
| **과금 방식** | **작업 실행 횟수당 차감 (operations 기반)** | **작업 실행 횟수당 차감 (tasks 기반)** |

## 5. 과금 방식 상세 (직접 확인 필요 ⚠️)

> **아래 내용은 반드시 공식 요금 페이지에서 최신 정보를 재확인하세요.**
> 요금 정책은 자주 바뀌므로, 보고서 제출 전 확인 권장드립니다.

| 도구 | 과금 단위 | 개념 |
|------|-----------|------|
| **Make** | **Operations(작업 수) 당 차감** | 모듈이 1번 실행될 때마다 1 operation 소모. 즉 **"실행 횟수당" 차감** 방식에 가까움 |
| **Zapier** | **Tasks(작업 수) 당 차감** | Zap의 액션이 1번 성공 실행될 때마다 1 task 소모. 역시 **"실행 횟수당" 차감** |

### 💡 정정: "Make=횟수당, Zapier=상시"는 정확하지 않아요!
- **두 도구 모두 기본적으로 "실행 횟수(작업 수) 기반"** 과금입니다.
- 다만 **차이점**은:
  - **Make**: 모듈(단계) 하나하나 실행마다 operation 차감 → 워크플로우가 길수록 더 많이 소모
  - **Zapier**: 트리거는 무료, **액션(task) 실행 시**에만 차감 → 단계 수보다 성공한 액션 수 기준
- **"상시 돌아간다"**는 개념보다는, 두 도구 모두 **트리거가 감지될 때마다 실행되고 그만큼 차감**되는 구조로 이해하는 게 정확합니다.

## 6. 결론

| 관점 | 추천 도구 |
|------|-----------|
| **복잡한 다중 조건 분기** | Make (Router 한 화면에서 관리) |
| **초보자 / 간단한 자동화** | Zapier (직관적 단계별 설정) |
| **연동 앱 다양성** | Zapier (6,000+ 앱) |
| **긴 워크플로우 비용 효율** | 케이스별 상이 (직접 계산 권장) |

### 본 프로젝트에서 느낀 점
- Make는 **조건 분기를 한 화면에서 시각적으로** 처리할 수 있어 편리했다.
- Zapier는 **조건마다 경로를 나눠야 해서** PASS/FAIL 구성 화면이 2개로 분리되는 번거로움이 있었다.
- 두 도구 모두 **실행 횟수 기반 과금**이므로, 워크플로우 설계 시 불필요한 단계를 줄이는 것이 비용 절감에 중요하다.
