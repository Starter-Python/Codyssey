# 노코드 자동화 도구 비교 분석 보고서
## — Make vs Zapier 기반 구글 폼 퀴즈 자동 채점 시스템 구현 —

---

## 1. 개요

### 1.1 프로젝트 목적
본 보고서는 노코드 자동화 도구인 **Make**와 **Zapier**를 활용하여 동일한 자동화 워크플로우를 각각 구현하고, 두 도구의 구조적·기능적 차이를 비교 분석하는 것을 목적으로 한다.

### 1.2 구현 대상 시나리오
구글 설문지(Google Forms)로 제출된 퀴즈 응답을 자동으로 수집하여 스프레드시트에 기록하고, 채점 결과에 따라 합격·불합격을 판정하여 디스코드(Discord)로 알림을 전송하는 자동화 시스템을 구현한다.

- **트리거:** 구글 폼 신규 응답 접수
- **처리:** 응답 데이터를 구글 스프레드시트에 저장
- **판정 기준:** 총점 8점 이상 시 합격, 8점 미만 시 불합격
- **결과 전송:** 합격 여부와 응답자·점수를 디스코드 채널로 통보

---

## 2. 자동화 구성

### 2.1 Make 구성

Make에서는 **Router(라우터)** 모듈을 사용하여 하나의 시나리오 내에서 합격·불합격 경로를 분기하도록 구성하였다.

```
Google Forms (Watch Responses)
        │
        ▼
     Router
   ┌────┴────┐
   │         │
[합격 경로]  [불합격 경로]
Google Sheets   Google Sheets
   │              │
   ▼              ▼
 Discord        Discord
(합격 메시지)   (불합격 메시지)
```

- **모듈 구성:** Google Forms → Router → (Google Sheets → Discord) × 2 경로
- Router의 각 경로에 필터 조건을 설정하여 총점에 따라 분기 처리
- 단일 시나리오 내에서 조건 분기를 완결적으로 처리 가능

### 2.2 Zapier 구성

Zapier 무료 플랜은 하나의 Zap에서 트리거 1개와 액션 1개만 허용하는 **2단계 제한**이 존재하며, 필터 분기 기능도 단일 조건만 설정 가능하다. 이에 따라 합격·불합격 처리를 위해 **두 개의 Zap을 별도로 생성**하였다.

**[불합격 처리 Zap]**
```
Google Forms → Filter (Total Score is less than 8)
             → Google Sheets → Discord
```

**[합격 처리 Zap]**
```
Google Forms → Filter (Total Score is greater than 7)
             → Google Sheets → Discord
```

- 필터 조건: 불합격 Zap은 `Total Score < 8`, 합격 Zap은 `Total Score > 7`(= 8 이상)로 설정
- 동일한 트리거를 두 Zap에서 각각 감지하여 조건에 맞는 경우에만 이후 단계 실행

## 3. 실행 결과

### 3.1 Make 실행 결과

Make로 구현한 시나리오를 실행한 결과, 디스코드 `#make` 채널로 채점 결과가 정상 전송되었다.

```
합격! [윈터]님 점수: [10]
불합격! [이동훈]님 점수: [2]
```

초기 구현 단계에서는 디스코드 메시지에 JSON 원본 데이터가 그대로 노출되는 문제가 있었으나, 매핑 필드를 응답자 이름과 총점 값으로 정제하여 최종적으로 가독성 있는 메시지 형태로 개선하였다.

## 4. 비교 분석

### 4.1 무료 플랜 제공량 비교

| 항목 | Make 무료 플랜 | Zapier 무료 플랜 |
|------|----------------|------------------|
| 월 제공량 | 1,000 크레딧(오퍼레이션) | 100 태스크 |
| 단계 제한 | 제한 없음 (여러 개 연결 가능) | 2단계 제한 (트리거 1 + 액션 1만 가능) |
| 활성 자동화 수 | 최대 2개 시나리오 | 무제한 |
| 확인 주기 | 최소 15분마다 | 최소 15분마다 |
| 실행 로그 확인 방식 | 실행 히스토리에서 모듈별 입출력 데이터를 시각적으로 상세 확인 | Task History에서 단계별 실행 내역 확인 |

### 4.2 분석

**(1) 단계 제한과 구현 방식의 차이**
Make는 단계 제한이 없어 Router를 통한 조건 분기를 포함한 다단계 워크플로우를 **하나의 시나리오**로 구성할 수 있었다. 반면 Zapier 무료 플랜은 2단계 제한으로 인해 본 과제와 같은 다단계·조건 분기 시나리오를 단일 Zap으로 구현할 수 없어, **합격·불합격 처리를 두 개의 Zap으로 분리**해야 했다. 이는 관리 포인트 증가와 중복 트리거 설정이라는 부담으로 이어진다.

**(2) 사용량 산정 방식**
Make는 월 1,000 크레딧으로 개별 오퍼레이션 단위 과금을 적용하며, Zapier는 월 100 태스크로 실행 단위 과금을 적용한다. 단순 실행 횟수 기준으로는 Make의 제공량이 월등히 크나, Make는 활성 시나리오가 최대 2개로 제한되는 반면 Zapier는 활성 자동화 수에 제한이 없다는 상반된 특성을 지닌다.

**(3) 구조적 자유도**
복잡한 분기·다단계 로직을 구성할 경우 Make가 유리하며, 단순한 2단계 자동화를 여러 개 운영할 경우 Zapier의 무제한 자동화 수가 유리하다.

## 5. 결론

| 구분 | Make | Zapier |
|------|------|--------|
| 강점 | 다단계·조건 분기의 자유로운 구성, 넉넉한 오퍼레이션 제공량 | 활성 자동화 수 무제한, 직관적 UI |
| 약점 | 활성 시나리오 2개 제한 | 무료 플랜 2단계 제한, 복잡 로직 구현 시 Zap 분리 필요 |
| 적합 상황 | 분기·다단계가 포함된 복잡한 워크플로우 | 단순 2단계 자동화를 다수 운영 |

본 과제와 같이 **조건 분기와 다단계 처리**가 필요한 워크플로우에서는 Make가 하나의 시나리오로 완결적 구현이 가능하여 관리 효율성과 구조적 자유도 측면에서 더 적합하다. 반면 단순한 트리거-액션 구조의 자동화를 다수 운영하는 경우에는 활성 자동화 수 제한이 없는 Zapier가 유리하다. 따라서 자동화 도구의 선택은 **워크플로우의 복잡도와 운영 규모**를 기준으로 결정되어야 한다.
